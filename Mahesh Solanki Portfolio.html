Approach

Build, break, repeat

Failure is the step that makes the next version better, so I give it its own stage.

Stage 1

Notice

Question the ordinary and look for problems worth solving.

Stage 2

Think

Research options and pin down the requirements.

Stage 3

Plan

Turn the observation into a concept and an approach.

Stage 4

Build

Write code, wire up tools, ship a prototype.

Stage 5

Fail

Find the bugs and the wrong assumptions. Learn from them.

Stage 6

Repeat

Refine, retest, and improve until it holds up.

Fail feeds back into Think. Repeat feeds back into Notice.

I enjoy systems where a language model does real work: reading a Google Drive, extracting data from a business card, routing a patient question to the right service. The model is the easy part. The rest is validated inputs, scoped tool access, and handling the case where something goes wrong.

How I write a defect report

The same fields every time, so a developer can act on it without a follow-up question.

Title
One line naming the feature and the failure.
Steps
Numbered actions that reproduce it from a clean state.
Expected
What the requirement says should happen.
Actual
What happened instead, with the exact message or screen.
Severity
How much it blocks the user, from cosmetic to blocking.
Retest
Result after the fix, plus nearby regression checks.
